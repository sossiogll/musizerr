# Musizerr — Architecture & Development Guide

## Philosophy

Musizerr is a **self-hosted, provider-agnostic music manager**. Every provider (metadata, download, storage, sync, lyrics) is a plugin that can be installed, removed, or replaced at runtime. The core system must never know which specific providers exist.

## The Golden Rule: Provider Agnosticism

**No provider lives in this repository, and no provider name may appear in `core/`, `services/`, `routes/`, `workers/`, `db/`, or frontend code.** The providers are packages of their own, in their own repositories, each with its tests and its image; the host runs them through the gateway (see below).

This means:
- No `if provider == "x"` checks
- No hardcoded provider name lists in defaults or constants
- No provider-specific UI sections (labels, icons, instructions)
- No provider code, no provider tests, no recorded responses of a provider's service, no provider's dependencies (`requirements-*.txt`, system packages) in this repository
- A provider imports `musizerr_sdk` and never the host (`providers/ → core/` does not exist as a dependency any more: there is no `providers/` here)

### Where provider names ARE acceptable
- **In `config.json`** and the settings (user data) — users configure their preferred order
- **In comments/docstrings** as illustrative examples (e.g. `# e.g. Identifier("provider_id", "abc", "catalog")`, preferably with invented names)
- **In the documentation of the gateway and the catalogs** as the example of an entry (`docs/gateway.md`, `docs/catalog.md`), and in the fixtures of their tests

### How to add a new capability

If a new provider needs a capability that doesn't exist in the interface (like an album-level dispatch), **extend the contract in `sdk/src/musizerr_sdk/interfaces.py`** with an optional method (default `raise NotImplementedError` or `return None`). Then the route code iterates generically over all providers. Never add `if provider.name == "x"` guards. The same goes for anything a provider needs from the host's paths: the provider DECLARES it (an `ExternalUtilityConfig.intake_name` for the credentials routes of a capture utility, `routes/external_utility.py`) and the host serves what is declared.

## The Host Boundary: Providers Don't Know the Infrastructure

The golden rule has a mirror image: the host never knows which providers exist, and **a provider never knows how the host works**. Only the host touches Redis, the database, Celery and the process environment. A provider imports **only `musizerr_sdk`** (`sdk/`, standard library only: the models, `Identifier`, the provider ABCs, `AuthDefinition`/`AuthSession`, `ProviderSetting`, `ProviderContext`, the exceptions it raises, the pure text helpers) plus the standard library and its own third-party dependencies. It talks to Musizerr only through:
- its `ProviderContext` (`self.context`, given at construction by the registry): its own settings (`settings()` / `setting(key)`), the HTTP, connect, download and stream start timeouts, and the public URLs the host serves for its covers and streams (`cover_url(id)`, `stream_url(id)`);
- the `AuthSession` passed to each call;
- the return values of the contract methods.

A provider may talk to its own upstream service (a remote API, a media server of the user) — never to Musizerr's infrastructure. This is what lets providers be packages of their own and run in a sandbox.

Consequences:
- **Providers declare constraints, the host enforces them.** Example: a download provider sets `max_concurrent_downloads`; the resolver takes a slot before calling it, and the host counts slots across workers.
- **Policy lives in the host, providers return data.** Example: `IdentificationProvider.identify()` returns its best match with a raw score; the host applies `identification_confidence_threshold` (`services/identification.py`).
- **Test a provider with `musizerr_sdk.context.StaticProviderContext`**, never by monkeypatching host modules; give the host its proxy (`tests.loopback.as_proxy`), never the provider.

`app/tests/test_layering.py` enforces the host side: no `providers` package exists under `app/` and nothing in it (tests included) imports one; the SDK sources import only the standard library and themselves; no host module imports the runner; only the registry imports the socket transport. The provider side (a provider imports no redis/celery/sqlmodel/sqlalchemy/alembic, no host package, no other provider, nothing of the protocol, the codec or the manifest, and reads no `os.environ`) is not checked from here any more: the sandbox makes it true at run time (nothing but the declared egress, no database, an empty environment) and the providers' repositories keep the static checks they want. There is no exception list: matching policy stays in the host, so a provider returns data (candidates, the tracks a package has) and the host decides — like `IdentificationProvider.identify()` returns a raw score.

### The host reaches a provider only through the call protocol

The host never holds a provider object, and it never looks at a provider's class. `ProviderRegistry` asks each provider the gateway runs (a **runner**, `musizerr_sdk.runner`, in the provider's sandbox; the runner builds the provider, never the host) to `describe` itself and registers a **proxy** (`services/provider_proxy.py`) built from the answer, the **manifest** (`musizerr_sdk.manifest`), under every role the manifest names. The proxy IS an instance of the abstract classes of its roles (type hints and the `ProviderRegistry` protocol hold), but it holds no provider code:
- **Declared, never inferred.** What the host used to read from a provider's class is manifest data: `name`, `label`, `auth`, `config_schema()`, `roles` (`proxy.roles`, a set of `metadata`/`download`/`lyrics`/`storage`/`sync`/`identification`: no `isinstance` on providers, and a sync provider that is also a metadata provider is filed under both), every capability (`musizerr_sdk.manifest.DECLARED_ATTRIBUTES` / `DECLARED_QUERIES`: `streams_full_tracks`, `supported_identifier_types`, `max_concurrent_downloads`, `supports_fuzzy`, `supports_stream_offset`, the `supports_*()` queries, `restricts_playlist_tracks()`, `is_library_available()`...) and `implements`, the optional methods the provider really overrides (`proxy.implements("search_playlists")`). These cost no call. A new capability is a new entry in those tables AND an optional method with a default in the SDK (a test fails when a `supports_*()` of the contract is in neither the tables nor the call samples); where the host used to infer something (`find_by_isrc` overridden), the SDK got a declaration (`supports_isrc_lookup()`).
- **Everything else is a call**, sent through a `Transport` (`services/provider_proxy.py`) as frames (`musizerr_sdk.protocol`: 4-byte big-endian length, a type byte for JSON or raw bytes, the payload): `{method, args, kwargs, session, context}` and, back, `result`, a stream or `error`. Every value goes through `musizerr_sdk.wire`, the lossless codec of the contract (explicit type tags, unknown tag = error; `core/serialization.py` stays the API view). An argument the codec cannot carry is a bug of the caller (`WireError`), not a failed provider. The **socket transport** (`services/provider_socket.py`) reaches a provider that runs in a sandbox behind the provider gateway (below) over its Unix socket, one connection per call; a connection that cannot be opened, breaks off or ends before the reply is complete is a `TransportError` (`unreachable`).
- **No callbacks into the host.** Each call carries a snapshot of the provider's context (`musizerr_sdk.context.ContextSnapshot`: its settings, the four timeouts, the public URL prefix), taken by `HostProviderContext.snapshot()` before the call; the runner builds the provider's `ProviderContext` from it for that call, per thread. A setting changed in the UI is seen by the next call. `CONTEXT_FREE_METHODS` (`supports_identifier`, a hot pure query) go without one. `python -m tests.provider_loopback_benchmark` (from `app/`, in a throwaway container) measures what the protocol adds to a call: about 17 us per track (with its identifiers) of a result, nothing for a declaration, about 12 us for a pure query, next to the tens of ms of the service the provider calls.
- **Streams** (`iter_saved_tracks`, `list_files`, `StorageStreamResult.chunks`) are produced as the host consumes them; an error in the middle is raised at the point of iteration; closing the iterator closes the provider's.
- **Errors.** The runner classifies the exception where its type exists (`musizerr_sdk.failures`: timeouts, HTTP status by `response.status_code`, the network; standard library and duck typing, no httpx). The exceptions of the contract (`DownloadDelegated`, `DownloadDeclined`, `DelegateHoldsRelease`, `RemotePlaylistGone`, `ProviderRateLimited`, `PermissionError`, `NotImplementedError`; `musizerr_sdk.wire.register_exception`) are raised on the host as themselves. Anything else is a `services.provider_proxy.ProviderCallFailed(kind, message, retry_after)` (`kind` is `None` when the type said nothing: the host then classifies the message text), which `services.errors.classify_error` reads directly. A lost connection (`TransportError`) is `unreachable`, a reply off the protocol `failed`. Host code never inspects a provider's raw exception (`httpx.HTTPStatusError.response`...): it reads `kind`.
- **Providers behind the gateway** (`gateway/`, `docs/gateway.md`, ADR-0006 phase 3). `provider-gateway` is a service of its own, host infrastructure that imports the standard library and `musizerr_sdk` only (`gateway/tests/test_layering.py`; the app never imports it, it talks to the control socket). It pulls an installed provider's image BY DIGEST (`installed.json`, until phase 4's catalogs), verifies every object and the `org.musizerr.provider.*` labels against the entry, unpacks the layers once (shared by digest) and runs one long-lived process per provider in a bubblewrap sandbox: read-only image root, private `/tmp`, fresh `/proc`, every namespace unshared (NO network), no capability, empty environment, rlimits from the manifest within the gateway's ceilings, an inner seccomp filter, only `<run>/providers/<name>` and `<workspace_dir>/<name>` mounted. No sandbox means no provider (`sandbox unavailable: <reason>` in `health`), never an unconfined run. The only way out is the provider's egress proxy (a Unix socket, reached through a loopback relay the runner starts): `egress` of the manifest (public addresses only) plus the destinations the CURRENT values of its `egress_from_settings` settings name, which the host sends the gateway before each call (`services/gateway_client.py`: `GatewayProviderContext`, `EgressGrants`; grants expire). The same grant carries the hosts of `tcp_from_settings` (a raw-TCP protocol such as FTP: any port or the declared range of the HOST the setting names, via `musizerr_sdk.net` CONNECT) and the folders of `filesystem_from_settings` (judged by `gateway/musizerr_gateway/filesystem.py`: absolute, normalized, an existing directory inside `GATEWAY_FILESYSTEM_ROOTS` after resolving links, never the gateway's own state; bound at the same path with the mode of the VERIFIED manifest; a change of binds restarts the provider); an `egress` entry may be a wildcard `*.example.com:443` (subdomains only, public addresses only, never in a name derived from a setting). `ProviderRegistry` registers only the providers the gateway lists as running (described through their own socket, checked against what their image declared, a mismatch is refused in `rejected()`); a gateway that does not answer is logged and the registry starts empty. `ProviderRegistry.reload()` rebuilds ONE process's registry (built apart, swapped in) and is called only by `services/provider_events.ProviderReloader`, which every process (the API and the three workers) runs on the Redis providers-changed event; the API announces (`announce_changed`: installs, and `GatewayWatcher` when the gateway's `epoch`/`generation` differs from what the registry loaded). The container needs the seccomp profile `gateway/seccomp/musizerr-gateway.json` (Docker's default plus `clone`, `mount`, `pivot_root`, `umount2`, `unshare`) and `systempaths=unconfined`, never `privileged`, never a capability.
- **Tests** have no real provider: they build a generic fake (`tests/conftest.py`: `FakeMetadataProvider`, `FakeSyncProvider`, `FakeDownloadProvider`, `FakeStorageProvider`, `FakeIdentificationProvider`, `FakeRegistry`; the shared ones of a topic in `tests/*_support.py`) and keep it (the provider side: what they set up and assert), and give the host `tests.loopback.as_proxy(provider)` (or `host_proxy(cls)`, the runner building it from the class). `tests/loopback.py` is the LOOPBACK transport, test infrastructure only: it runs a runner in the test's process and every request and reply is a frame, nothing is passed by reference. `tests/host_boundary.py` fails a test in which host code reads a provider instance, and `test_layering.py` allows no host module to import the runner. What a provider does with its own service is tested in the provider's repository, never here. The rules that hold for EVERY provider and that the host can no longer check over a registry (it holds no provider, and the providers live in their own repositories) are `musizerr_sdk.conformance`, run by each provider's own test suite on its instance: `check_provider(MyProvider(StaticProviderContext()))` raises one `ConformanceError` (an `AssertionError`) that lists every violation — `config_schema()` well formed (types the host knows, unique keys, enum options, defaults of their type, `visible_when` naming declared keys) and an OAuth2 provider that declares a capability that writes on the user's account (`CAPABILITIES_NEEDING_A_SCOPE`) mapping it in `OAuth2Config.capability_scopes`. A new generic rule goes there, with a good and a bad sample provider in `sdk/tests/test_conformance.py`; see `docs/provider-authors.md`.

### Files cross the boundary through workspaces

A provider never sees or returns a host path. For every call that produces or reads a file, the host creates an empty workspace directory (`services/workspace.py`, under the `workspace_dir` setting) in the folder of THAT provider, `<workspace_dir>/<provider>/<random>`, passes it in, and the provider returns only names relative to it. A sandbox sees only its provider's folder (as `/workspace`); an operation that tries several providers (a download) gets one workspace each (`open_workspaces`), and a file that goes from one provider to another (downloaded by one, stored by another, held for a later upload) is staged by the socket transport into the second one's folder for the call (`services/provider_socket.py`, which also rewrites the paths it sends: the `workspace` argument and `WorkspaceFile.workspace`). The sweep (`remove_stale_workspaces`) walks the provider folders and leaves them, and `held-uploads`, in place. The host decides the final library path, rejects names that escape the workspace, and removes the workspace when the operation ends. See `docs/adr/0003-provider-file-exchange-workspace.md`.

External providers (images) declare `provider_api_version` (4 declares `account_model` on every `AuthDefinition`; **5** moves the contract into the `musizerr-sdk` package: OAuth2 auth strategies are declarative data the host implements, `config_schema()` returns `ProviderSetting` and the legacy `ConfigField` and the `providers/*.py` re-export modules are gone); a catalog entry for another version is listed but not installable and the gateway refuses an image that implements another one (`musizerr_sdk.interfaces.PROVIDER_API_VERSION`). The SDK's major version is the contract version (`sdk/pyproject.toml`: 5.x.y). **Within a major the contract only grows, and never breaks a peer built on another minor** (ADR-0007 §3.1, `musizerr_sdk.version`): the wire codec ignores a field it does not know and gives a missing one its default; a field added after the first release of the major carries `field(default=..., metadata={wire.SINCE: "5.5"})` (a default is required, `wire.register` refuses one without); the manifest says the SDK a provider was built on (`Manifest.sdk_version`, label `org.musizerr.provider.sdk-version`) and every request the host's (`"sdk"`), and each side encodes for the other (`wire.encode(value, peer)`: `ProviderProxy` for the provider's, the runner for the host's), a peer that says nothing being 5.4 (`BASELINE`), so an image built before 5.5, which decodes strictly, keeps working. `sdk/tests/test_contract_evolution.py` and `app/tests/test_provider_contract_evolution.py` hold it. A new enum member or a new wire type is not such an addition: it travels only through a new optional method or capability the peer declares.

### Where the providers live

None of them is in this repository. The first-party providers are in two others, each provider a package with its tests and its image (`FROM` the base image of `provider-base/`, labels from `scripts/build-provider-image.sh`):

- `musizerr-providers`: the public ones (lyrics, metadata, download, storage, sync and identification providers that carry no concern for the project);
- `musizerr-providers-private`: the ones kept private.

Both are built against the `sdk/` and the base image of this repository (`scripts/dev-catalog.sh <provider-dir>...`, the directories may be anywhere on the machine) and installed through a source (`docs/catalog.md`) into the gateway (`docs/gateway.md`); the registry registers what the gateway runs and nothing else. So a host test never has a real provider: it builds a generic fake and gives the host its proxy (see "Tests" above), and a provider test never has the host: it uses `StaticProviderContext` and the SDK. A third party starts from the template repository `musizerr-provider-template` (an example provider, its tests in the base image, publishing to GHCR and `catalog.json`); the guide is `docs/provider-authors.md`.

### Layering

Dependency direction is one-way: `routes/` and `workers/` call into `services/`; `services/` calls `core/`/`db/` and, to dispatch a Celery task, imports only `workers.celery_app` (never `workers.tasks` or another task module — it dispatches by the task's registered name, e.g. `celery.send_task("workers.tasks.download_task", ...)`). `providers/` depends only on `musizerr_sdk` (see the Host Boundary above). `core/` never imports `db/`, `services/`, `routes/`, `workers/`, or `providers/`: it holds the host's domain logic (the provider contract itself is `musizerr_sdk`, which `core/` imports and never the reverse; the SDK imports only the standard library), and everything that touches persistence or infrastructure (`ConfigManager`, the registry, credential routing, workspaces) is host code in `services/`.

`app/tests/test_layering.py` enforces every one of these rules by walking the actual imports (`ast`, including ones inside function bodies) — it fails on a violation, not just a lint warning.

When moving a function or class to another layer, migrate every caller — routes, workers, tests (including lazy imports and `monkeypatch`/`mock.patch` targets) — and delete the old definition. Never leave a re-export shim at the old path.

## Do's and Don'ts

### Backend

**Do:**
- Add new provider capabilities as optional methods in `sdk/src/musizerr_sdk/interfaces.py` with sensible defaults (and bump the contract version when a provider has to change)
- Use the registry to discover providers dynamically (`registry.all_download()`, `registry.all_metadata()`)
- Use `MatchResult` with `reason` field for match decisions — it enables fallback logic
- Keep enrichment functions centralized in `services/enrichment.py`
- Document every new or changed route in `app/openapi.yaml` (served at `/openapi.yaml`); `app/tests/test_openapi_spec.py` fails when a route is missing or stale
- Use `musizerr_sdk.text.normalize()` for text comparison (public API: providers use the same function)
- Return file paths from download methods, not provider-specific objects
- Declare auth requirements via `AuthDefinition` — flow AND account model (`account_model`) — the `AuthManager` handles the flow generically and the store routes the account

**Don't:**
- Import anything from `providers/` in `core/`
- Hardcode provider names in config defaults, route logic, or worker logic
- Add provider-specific fields to domain models (use `external_ids` with `Identifier`)
- Duplicate enrichment logic in route handlers — use the centralized `services/enrichment.py` functions
- Create private functions in `core/` that are needed elsewhere — make them public

### Frontend

**Do:**
- Use `SettingsContext` for provider labels and config values (priority, order)
- Get provider metadata from the `/providers` API endpoint (`ProviderInfo.label`, `ProviderInfo.auth_flow`)
- Pass `metadata_provider_priority` from config when ordering or selecting providers
- Gate playback UI on both `preview_url` AND `stream_url` — tracks can be playable via either source (preview from metadata providers, full stream from sync providers)
- Put what a track, album, artist or playlist can do in its ONE contextual menu (`components/menu/`: `ActionMenu` is the "⋯" button, right click and long press; `TrackMenu`, `CollectionMenu`, `UserPlaylistMenu` build the entries from the capabilities, `download_policy` and states the server reported). A new action is a new entry there, never another per-row button or dropdown; the quick controls that show a state (the status slot, the heart) stay beside it

**Don't:**
- Create hardcoded provider name → label mappings
- Hardcode provider priority lists — read from config
- Build provider-specific UI sections outside of declarative/data-driven patterns

### Database & Migrations

- Use Alembic for all schema changes (see `docs/migrations.md` for full details)
- Never use `SQLModel.metadata.create_all()` directly — `init_db()` runs `alembic upgrade head`
- New migrations go in `app/migrations/versions/` with sequential numbering (`0004_...`)
- After changing `app/db/models.py`, generate a migration:
  ```sh
  cd app && alembic revision --autogenerate -m "short description"
  ```
- Review the generated file — add `server_default=...` for NOT NULL columns on existing tables
- `env.py` uses batch mode (`render_as_batch`) on SQLite only (copy-rename for ALTER operations); PostgreSQL alters in place. The database URL comes from the same resolution as the app's (`db.engine.database_url()`)
- Startup handles three cases automatically: fresh DB, pre-alembic SQLite DB (stamps baseline then upgrades; a PostgreSQL database is never stamped), and already-managed DB. On PostgreSQL the whole upgrade is one transaction under an advisory lock
- **Two databases, one code.** `DATABASE_URL` (PostgreSQL, `postgresql+psycopg://...`) or, unset, the SQLite file `DATA_DIR/musizerr.db`; `db/engine.py` is the ONE place that sets an engine up (`make_engine`: SQLite WAL/busy timeout, PostgreSQL lock/statement timeout, pool) and the one that resolves the URL (app, workers, scripts, Alembic, the migration tool). No SQL only one of them understands: what differs lives in `db/expressions.py` (`ascending`/`descending` fix the NULL order of a nullable column, `json_number`), a migration never uses `PRAGMA`/`GROUP_CONCAT`/`= 1` for a boolean, a partial unique index declares `sqlite_where` AND `postgresql_where`
- **Writers race on PostgreSQL** (SQLite lets one in at a time). A rule a unique constraint can express is an `INSERT ... ON CONFLICT` (`db/upsert.py`: `insert_ignore`, `upsert`), never "look, then insert"; one it cannot takes `db.locks.xact_lock(session, name)` first (the track two identifiers resolve to, a download request per track, a routine claim per period). `tests/test_concurrency.py` races each of them. A claim is one conditional `UPDATE`. Foreign keys are enforced: write a parent before its children (flush), delete children before the parent, and a row that points at the instance's synthetic user needs that user's row (`user_service.ensure_system_user`)
- `docs/postgresql.md` has the variables, the switch from SQLite (`scripts/migrate_sqlite_to_postgres.py`: dry run by default, verifies a checksum of every column of every row, one transaction) and how to go back. A script never opens SQLite itself: a dry run is `db.engine.atomic_session(commit=False)`

### Docker

- The host machine runs macOS with Python 3.9.6 — **do not run Python directly on the host**
- Use `docker exec musizerr-app-1 python ...` for validation
- Use `docker exec musizerr-frontend-1 npx tsc -p tsconfig.app.json --noEmit` for TypeScript checks — the root `tsconfig.json` declares `"files": []` plus a project reference (needed for the existing Vite project-reference layout), so plain `tsc --noEmit` from the root analyses zero files and always reports success. Point `-p` at `tsconfig.app.json` directly to actually check the app source.
- Node/npm must run inside Docker containers, never installed on the host
- The provider contract is the `musizerr-sdk` package (`sdk/`, standard library only). The `Dockerfile` copies it to `/sdk` and installs it editable (`pip install -e /sdk`) before the application code; the dev compose mounts `./sdk:/sdk` next to `./app:/app` (uvicorn and watchmedo watch both). Its own tests run without the host: `docker exec musizerr-app-1 sh -c 'cd /sdk && python -m pytest'`
- The gateway and the integration tests run in containers too: `docker run --rm -v $PWD:/repo -w /repo/gateway musizerr-app sh -c 'pip install -q -e /repo/sdk -e /repo/gateway && python -m pytest tests'`; a provider's own tests run from its repository (`musizerr-providers/scripts/test.sh`). `scripts/test-gateway-integration.sh` builds real images and runs real sandboxes under its own compose project (`mzp3`, docs/gateway.md); `scripts/test-sources-integration.sh` (`mzp4`) and `scripts/test-provider-infra-integration.sh` (`mzp51`: wildcards, raw TCP, folders from settings, the dev catalog script) do the same. The first two need a real provider image to install: they build the lyrics provider of the public providers repository (`PROVIDERS_REPO`, default `../musizerr-providers`, only read). `INTEGRATION_PROJECT` and `INTEGRATION_REGISTRY_PORT` rename the compose project and the local registry's port of those two when two runs must not meet. The provider images are built with `scripts/build-provider-image.sh`; `scripts/dev-catalog.sh <provider-dir>...` (directories may be anywhere on the machine) builds them, pushes them to the local `oci-registry` and writes the development catalog under `data/catalogs/` that the dev `registry` service serves — the repository itself lists no provider; nothing is ever pushed to ghcr.io or Docker Hub by either. Publishing is apart: `scripts/publish-provider-base.sh` and `scripts/publish-provider-image.sh <provider-dir> <catalog-file>` (called by each providers repository's `scripts/publish.sh`) build for linux/amd64 and linux/arm64 and push to GHCR, the catalog pinning the digest of the multi-architecture index (`docs/catalog.md`, "Publishing to GHCR"); a new package is private and no script changes a visibility
- `docker-compose.yaml` (production) builds nothing: it runs the images published on GHCR (`x-images`: `${MUSIZERR_IMAGES:-ghcr.io/sossiogll}/musizerr`, `musizerr-gateway`, `musizerr-frontend` at `${MUSIZERR_VERSION:-latest}`; `.github/workflows/images.yml` publishes `:latest` on every merge into master and `:X.Y.Z` on a tag `vX.Y.Z`). `docker-compose.build.yml` on top of it builds them from the checkout instead (`musizerr:local`...). `docker-compose.dev.yml` keeps building and mounting the sources
- The compose files run a `postgres` service (named volume `postgres_data`, healthcheck) and give `DATABASE_URL` to `init`, `app` and the workers; `POSTGRES_PASSWORD` is required, comes from `.env` (never committed, see `.env.example`). Inspect it with `docker compose exec postgres psql -U musizerr`
- `AUTH_SECRET` is required too (compose `${AUTH_SECRET:?...}`, in `.env`): with `auth_enabled` the app refuses to start on a missing, empty, short (<32) or placeholder secret (`user_auth.require_strong_secret`, called once in `main.lifespan`, and by `SettingsService.write_values` through the `guard_on` of the `auth_enabled` catalog entry when a write turns authentication on: 400 `auth_secret_insecure`; no bypass flag, see `docs/permissions.md`). The test suite's `AUTH_SECRET=test` is fine because it never starts the app with authentication on
- `CREDENTIALS_KEY` is required too, and unconditionally (compose `${CREDENTIALS_KEY:?...}` on `init`, `app`, the workers and beat; plus the optional `CREDENTIALS_KEY_PREVIOUS` while a key is rotated; never on the gateway): every stored credential (`provider_credentials.data`, `provider_sources.credential`, the value of every `SettingDef.secret` setting) is sealed with it (`enc:v1:` + a Fernet token, `core/secret_box.py`; `db/credential_cipher.py` reads the environment and is the only module that names the variables, `tests/test_layering.py`). The API (`main.lifespan`, before `init_db()`) and every worker/beat (`workers/celery_app.py` at import) refuse to start without a valid one; migration `0041_encrypt_credentials` needs it too and seals the existing rows. A value no configured key opens (or one in clear at run time) is, for its reader, NOT THERE — an account "not connected", a source with no token, a setting at its default — reported once, secret-free, never returned as text and never overwritten by a read. Losing the key means reconnecting the accounts: back it up with the database. Rotation: `python -m scripts.rotate_credentials_key [--apply]`. `docs/credentials.md` has all of it. The suite forces a fixed public test key in `tests/conftest.py` (`tests/credentials_support.py`); a test about keys uses `use_keys`
- The backend suite runs on SQLite (default, in memory) and on PostgreSQL (`TEST_DATABASE_URL=postgresql+psycopg://user:password@host:5432/postgres`, a user that can create databases): one clean database per test from `tests/database.py` (`new_engine()` or the `engine` fixture), never an inline `create_engine`. A test about one engine only is `@pytest.mark.sqlite_only("reason")` / `postgresql_only("reason")`. Both suites must pass

## Provider Contract Summary

All of it lives in `musizerr_sdk` (`musizerr_sdk.interfaces`; the types in `musizerr_sdk.models`, `.identifiers`, `.auth`, `.context`, `.settings`, `.errors`, `.delegation`, `.capabilities`, `.text`; and `.conformance`, the checks its own tests call) — a provider imports nothing else of Musizerr.

```python
class BaseProvider(ABC):
    __init__(context: ProviderContext)                          # self.context: own settings + timeouts
    config_schema() -> list[ProviderSetting]                    # the settings it declares (key, type, default, label, options, ...); the host places them under the provider (key, group, area, scope)
    permissions: Permissions                                    # what the sandbox may grant (data, in the manifest and the image labels): egress ("host:port", the host may be a wildcard "*.example.com"), egress_from_settings (setting keys), tcp_from_settings (setting key + ports: raw TCP to its host), filesystem_from_settings, limits; nothing by default
    supports_login() / identify_account(session) -> AccountIdentity | None  # optional: a user may sign in through their own account of it (declared; the provider's stable id, never an email); see "Sign-in through a provider"

class MetadataProvider(BaseProvider, ABC):
    streams_full_tracks: bool = False                            # its stream_url is the full track (host: playback source "provider")
    # All methods have defaults (return []/None), override as needed:
    search_tracks/albums/artists/playlists(query, session, limit)
    get_track/album/artist/playlist(provider_id, session)
    supports_isrc_lookup() -> bool                              # declared, never inferred: find_by_isrc is implemented (the host asks these before a text search)
    find_by_isrc(isrc, session) -> Track | None
    find_related_tracks(track, session, limit) -> list[Track]      # variants of the same recording
    find_similar_tracks(track, session, limit) -> list[Track]      # other recordings: artist radio, recommendations
    get_artist_albums(provider_id, session, limit) -> list[Album]  # pages inside the provider until `limit` or the end; the host asks for 100-200, never a search page size
    supports_discography() -> bool                                # declared, never inferred: it lists an artist's releases (get_artist_albums) AND gives each release's tracks (get_album); a library listing (a sync provider) answers False. Gate of POST /download/artist
    get_artist_top_tracks(provider_id, session, limit) -> list[Track]  # most popular, provider order
    supports_user_library() / get_saved_tracks(session, limit, offset)  # the likes the user has on the provider
    iter_saved_tracks(session, page_size) -> Iterator[list[Track]]  # how the host imports the likes, one list per page; default pages get_saved_tracks by offset until a short page; override when the service pages by cursor or costs quota per call (the provider decides where the library ends, an empty page is not the end)
    supports_unlike_saved_track() / unlike_saved_track(provider_id, session)  # optional: take a like off (personal setting unlike_on_origin_providers); PermissionError = reconnect
    get_preview_url(provider_id, session) -> str | None            # a signed preview URL valid NOW; the track carries context.preview_url(id)
    get_playlist_snapshot(provider_id, session) -> str | None      # optional: the version marker of a playlist WITHOUT its tracks; the host reads the tracks again only when it changes (None = no cheap marker)
    restricts_playlist_tracks() -> bool                            # declared: the service shares the tracks only of the playlists the account owns or collaborates on (capability playlist_tracks_restricted); an unreadable one comes back with Playlist.tracks_unavailable

class DownloadProvider(BaseProvider, ABC):
    supported_identifier_types: set[str]
    max_concurrent_downloads: int | None                        # declared limit, enforced by the host
    supports_fuzzy: bool = False                                # declares a real download_fuzzy (never inferred)
    download_by_id(identifier, workspace, session) -> str | None  # abstract; file name inside workspace
    download_fuzzy(track, workspace, session) -> str | None       # optional; same contract
    # None = "I don't have it" (definitive); raise = upstream unreachable/5xx (the host retries later);
    # raise DownloadDelegated (handed to an external system) or DownloadDeclined(code) (definitive, with a reason)
    # raise DelegateHoldsRelease(handle, tracks, complete, release, details, state) when the external system ALREADY holds the track's release: data only, the host decides (`core.download_resolver.download_fuzzy`: the track has a file -> delegated; the release is complete without it -> DownloadDeclined `already_in_delegate`; else `search_delegated(held, session)`, which raises DownloadDelegated)
    dispatch_album(album, session) -> None                      # optional, raises DownloadDelegated
    poll_delegation(handle, session) -> DelegationStatus | None   # optional; the state of the delegated package as a whole (None = fire-and-forget)
    list_delegated_tracks(handle, session) -> list[Track]        # optional; the tracks of the package that already have a file, as data (album empty = the delegated release); the host decides whether the requested track is one (`services/delegation.poll_for_requested_track`, `pair_album_tracks`) and then it is DOWNLOADED before any package-level signal

class StorageProvider(BaseProvider, ABC):
    supports_stream_offset: bool = False                          # stream() takes offset=: the host answers Range with 206
    store(source: WorkspaceFile, relative_dest, session) -> str
    exists(relative_path, session) -> bool
    stream(relative_path, workspace, session) -> StorageStreamResult  # file in workspace | url | chunks (+ size, offset); a remote file as chunks, never downloaded first
    list_files(prefix, session) -> Iterator[str] | None       # optional; relative paths, None = cannot list

class SyncProvider(BaseProvider, ABC):
    trigger_scan(session) -> None
    find_candidates(track, session) -> list[SyncCandidate]        # the tracks of its library that might be `track`, each with its sync id (SyncCandidate(sync_id, track)); how it searches its API is its own, WHETHER one is the track is the host's (`services/enrichment.check_sync_availability`, `find_match`)
    get_stream_url(sync_id, session) -> str | None
    like_track(sync_id, session) / unlike_track(sync_id, session)  # optional; favorites propagate here
    supports_playlists() / create_playlist(name, sync_ids, session) -> remote_id / update_playlist(remote_id, name, sync_ids, session) / delete_playlist(remote_id, session)  # optional (default: not supported); the user's playlists mirrored on THEIR OWN account; update is a replacement; RemotePlaylistGone = it is not there any more
    list_library(session) -> list[LibraryItem]                  # optional; the whole library, indexed by services/sync_index.py
    fetch_partial(sync_id, workspace, session, max_bytes) -> str | None  # optional; file name inside workspace

class IdentificationProvider(BaseProvider, ABC):
    identify(audio: WorkspaceFile) -> Identity | None           # best match + raw score; the host applies the threshold
```

## Key Patterns

- **Identifier system**: `Identifier(type, value, provider)` — data-driven, no class hierarchy. Defined in `musizerr_sdk.identifiers`; how the host reads identifiers to decide which record a track is stays in `core/identifiers.py`. Types: `isrc` (universal), `mbid` (universal), `provider_id` (provider-specific)
- **Cross-enrichment (track)**: ISRC exact match → MBID match (with year guard) → shared provider id (same item, including a sync id) → fuzzy (title identity + one artist in common + confirmations)
- **Track identity** (`core/matching.py`): the version is part of the title identity — `version_identity`/`title_identity_key`: a remix, live, mix, edit, acoustic... tail never matches another version of the same song; `feat.` credits and edition markers (remaster, year, explicit) are not versions. A duration beyond the tolerance (`duration_tolerance_ms`: 3 s or 2%) rejects; a year one apart is tolerated only when album and duration agree. Count "by song" with `title_identity_key`, never with a bare base title (`base_title_key` only narrows candidates)
- **Cross-enrichment (album)**: `cross_enrich_album` enriches album-level data AND individual tracks. When a matching album is found on another provider, `_enrich_album_tracks` fetches the full album and pairs its tracks with `core.matching.pair_album_tracks`: one to one, same title identity, `match_track` first, then same disc/track number, then the closest duration; a title alone pairs only when it appears once on each side (never when several tracks share it). On a `track_count_mismatch` (standard vs deluxe) album-level enrichment is skipped but track pairing still runs — except for an album of a sync provider, which lists the files the library holds: its track count is never taken (`catalog_view`) and with a different count its tracks enrich nothing. Provider-scoped ids (`artist_provider_id`, `album_provider_id`) are merged only from the same provider (`core/merge.py`)
- **Identity resolution** (`core.identifiers.resolve_identity`, used by `services/track_state.py` and `db.track_store`): the best-ranked shared identifiers decide — ISRC/MBID, then provider ids, then sync ids; identifiers of the same rank on different records are `AMBIGUOUS` (the read path claims no record; `find_or_create_track` takes the oldest). A provider registered as sync provider has ONE identity space: its provider id and its sync id are the same value (`services/track_identity.py`: `with_sync_aliases` at import, download and indexing; `alias_pairs` when resolving). A new sync id replaces the stale one of the same sync provider on a record (`add_identifiers`, unless the caller holds the whole live listing and settles stale ids itself: `services/sync_index.py`). The availability on the sync provider is decided by the identifiers a row carries, never by the presence of a stream URL
- **Identifiers have one home: `track_identifiers`.** `tracks.track_data` never carries `external_ids` (`stored_track_data` does not write them, `track_data_dict` ignores them in an old payload, migration 0025 removed the copy); a list row gets its identifiers from the table (`services.stored_tracks.public_track_dicts`, `db.track_store.load_track` / `identifiers_by_track`; `track_from_record(record, identifiers)` takes them explicitly). `add_identifiers` is the only writer for an existing record and its input is evidence gathered from a live source, never read back from a stored payload. See `docs/adr/0005-identity-data-and-reads.md`
- **Reading never writes.** No GET touches the database: `annotate_tracks`, `known_track_ids` and every route that uses them only read. A track a sync provider answered for during a request can play (a sync provider streams whole tracks) but is not "in the library" because of it. The sync presence is written by jobs in `services/sync_index.py` — `index_library` (the whole `SyncProvider.list_library`: a record with its sync id for every live file, stale ids dropped when the record stays explained, never on a partial or empty listing, a record with two live files keeps both) runs as its own routine `sync_library_index` (hourly on the `jobs` queue, and started by a library scan or a likes sync through `services.routines.start_routine`): one report per sync provider in its result, and a provider that fails or a listing guard makes the run `error` with a stable code (`sync_provider_<kind>`, `sync_provider_empty_listing`/`_partial_listing`), never `ok` with a hidden warning. The like matching (`match_likes`) follows it and never indexes; its result says how the last index ended (`library_index`). `index_track` asks about one track (the download worker, the likes download). `tests/test_identity_stays_clean.py` reads every kind of page many times in any order and asserts the database and the coverage do not change
- **Removed favorites** (`RemovedFavorite`, `db/favorite_store.py`, `services/favorites.py`): taking a favorite off remembers the song by `core.matching.song_keys` (its stable identifiers and, per artist, its title identity — never a sync id, never a record id), so the like matching and the likes download never bring it back, whichever record the like resolves to (a re-import after a merge or split, "Elimina dati libreria" followed by a sync, a like still on the origin provider). Only the user's own heart or download clears it (`favorites.add` / `register_intent`). Optionally `MetadataProvider.unlike_saved_track` takes the like back on the origin provider too, where the API allows it: `unlike_on_origin_providers` is a PERSONAL setting (scope `user`, off by default, read with `services.settings.personal_value`) of the user who removes the favorite, and the task (`workers.maintenance.unlike_on_origin_providers`) uses only that user's own account (`services.credentials.own_store`: an `own_only` store, so `AuthManager.authenticate` never reaches the shared account nor an app-only token), never another user's. Its result lists each provider's outcome and reason
- **Accounts** (`musizerr_sdk.auth.AccountModel`, `db/auth_store.py`, `services/credentials.py`, `services/linked_accounts.py`, `routes/auth.py`): every provider DECLARES whose account it is used with in `AuthDefinition.account_model` (required; `none` / `personal` / `personal_with_shared` / `system`; the host never infers it from the category or the flow, and a flow that cannot be personal, i.e. an API key or an external utility, cannot declare it). ONE rule routes every READ of a credential (`CredentialStore`): `personal` = the user's own row; `personal_with_shared` = the user's own, else the shared one (`user_id` NULL); `system` = the shared one; a store with no user (host jobs, a guest) sees only the shared one; an `own_only` store (`own_store`: importing or taking back a user's likes, propagating a favorite) never sees it, nor an app-only token. WRITES never route: the caller names the `AccountTarget` (`personal` or `shared`; `shared` is the admin's, only where the model has one), so an admin connecting their own account never writes the instance's (there is no copy of one into the other). A disconnected account is a deleted row; a token refresh is a compare-and-swap over the row it was read from (`replace_oauth2_token`; the text compared is the SEALED one). EVERY credential is stored sealed (`provider_credentials.data`, `docs/credentials.md`): `CredentialStore` seals on write and opens on read, and a row the configured keys cannot open is simply not there for any reader (no account, no client, no key; `get_external_utility_accounts` says `{}`) — connecting again replaces it, and a read never rewrites it. `GET /auth/linked-accounts` lists, for any signed-in viewer, the providers whose model has personal accounts and what is connected; `GET /providers` carries `account_model`, `personal` and `shared` (who the shared account is only for admins); `/auth/{provider}/{authorize-url,start,credentials,test}` and `DELETE /auth/{provider}` take `target`. The UI: Settings › Linked accounts (any viewer, capability `linked_accounts`) and Administration › Providers (admin), both data-driven from the declaration (a login form is the provider's `credential_fields`). `docs/permissions.md` has the matrix
- **Sign-in through a provider** (`core/provider_login.py` the rules, `services/provider_login.py`, `routes/provider_login.py`, `services/login_rate_limit.py`, `docs/provider-login.md`): a provider with personal accounts that declares `supports_login()` and answers `identify_account(session)` (its stable id for the account) can sign users in; `GET /auth/account/login-providers` lists them (an OAuth2 one once its app is set up), the login page renders one button per entry (an OAuth2 provider) or the provider's own `credential_fields` form, never a name. Linking is ONLY from an open session (the linked-accounts flow stores the id in `provider_credentials.external_id`, unique per provider); a sign-in finds the user by that id and NEVER by email, name or username. An id nobody linked is governed by the admin setting `provider_login_new_accounts` (`disabled` default / `pending` / `active`, system scope); the account created is always a `user` (the admin role never comes from a provider) with an unusable password, and `pending` ones wait (`users.pending_approval`, activated from Administration › Users). The OAuth2 callback is the existing one: its state says linking (`oauth_state`) or sign-in (`oauth_login_state`: provider + hash of a nonce also held in an HttpOnly cookie, both needed), and it ends on `/login/provider` with a one-time code (`provider_login_codes`, 60 s, hash only, spent by one conditional UPDATE) the page exchanges for a session issued by `refresh_tokens.start_session`, the same as a password. The sign-in routes share a per-address Redis limit. A service may cap the users of an app in development mode (see `docs/provider-login.md`)
- **Provider capabilities** (`musizerr_sdk.capabilities`): a metadata provider declares optional capabilities with `supports_*` (`core.interfaces.metadata_capabilities`); GET /providers lists them (`capabilities`), a setting names the one it acts through (`SettingDef.provider_capability`: the UI lists the supporting providers and the viewer's own account state). An OAuth2 provider maps a capability to the scopes it needs (`OAuth2Config.capability_scopes`, requested on every new connection); a connection granted before a scope existed is reported in `missing_permissions` and the UI asks to reconnect
- **Library coverage**: ONE computation, `core.download_states.song_coverage`, for the album/playlist page (`collection_summary`, a row per song) and every discography/Home tile (`services/library_coverage.py`, library records keyed by `title_identity_key`). The total of a release comes from catalogs only (never a sync provider's count); unknown → `total: null` and the UI says "N in library", never N/N
- **Download requests** (`services/downloads.py`, one gate for every entry point: track, retry, album, playlist, artist, likes sync, the transient-failure routine): a track in the library never gets a new download (`already_in_library`, unless an admin sends `force`); a track with an open request joins it (`attached`); the task receives the CANONICAL track with all its identifiers (`task_track_data`), never only the requesting row's. The worker re-checks the library before downloading. When the task message cannot be sent (broker down) the gate does not leave an open `pending` row nobody will run: the Download ends `failed`, `retriable`, with the `queue_unavailable` marker (`db.download_store.mark_unqueued`, error code `queue_unavailable`), so `file_state` shows it, a later request gets a download of its own and `retry_transient_failures` queues it again — for every caller, approvals included
- **Download approval policy** (`core/download_policy.py` the pure rules, `services/download_requests.py` the use cases, `services/request_policy.py` where the policy comes from, `db/download_request_store.py`): every USER-FACING way to ask for a download — `routes/content/{track,album,playlist,artist}.py` and the likes-download job (`workers/tasks.py`, kind `liked_elsewhere`) — calls `download_requests.request_download` BEFORE anything is queued or delegated, then runs through the gate above (`execute`: `enqueue_track`, `enqueue_tracks`, `downloads.download_album` with its `dispatch_album` delegation). The kind is `track`/`album`/`playlist`/`artist`/`liked_elsewhere`; each has a mode, `auto` / `approval` / `auto_up_to` N, and a user has a quota of tracks per rolling window. The count a rule judges is the tracks that NEED a download (`needed_tracks`: never the ones in the library or with an open download the request would attach to). A request that needs nothing, an admin's, and any request with authentication off are not governed and not recorded; every other one is recorded in `download_requests` (`pending`/`approved`/`denied`/`cancelled`, `auto`, `reason` in `core.download_policy.REASONS`), the ones approved at once too. A waiting request queues, delegates and registers NOTHING (no favorite intent either): the tracks (and the album, for a delegation) are stored in its `payload` and run through the same gate on approval, so a denied or cancelled request leaves no pending heart and nothing in the track catalog. Two levels: the GENERAL policy is the `download_request_*` settings of the catalogue (generated from `download_policy.KINDS`, `scope="system"`, edited with `PATCH /admin/download-policy` or the settings page), a user's OVERRIDE is a row of `user_request_policies` (a settings row of scope `user` would be written by the user themselves; only an admin writes it: `PUT /admin/users/{id}/download-policy`). The quota counts the approved requests in the window, `queued_tracks` (what the gate actually queued) or `needed_tracks` while it is still being queued. Deciding is ONE conditional UPDATE (`store.claim`, `WHERE status = 'pending'`): of concurrent approvals, denials and cancellations of a request exactly one wins and only the winner queues; a new request is decided under `xact_lock("download-request-user:<id>")` with its quota reserved before queueing. A RETRY is not a request: it re-runs a download that exists, so a governed user may only retry a track they have a download of (`may_retry`, 403 `retry_not_approved` otherwise); the routines (`retry_transient_failures`) are not governed. `GET /auth/account/status` reports `download_policy` (per kind `auto_up_to`: the most tracks that go at once right now, quota included) so the UI labels the button; the server stays the only judge. Notifications reuse `/progress`: `{"type": "download_request", "event"}` to the requester with `user_id`, to the admins without it. Never add a download entry point that skips `request_download`
- **Download approval policy in the UI** (`hooks/useDownloadApproval.ts`, `lib/download-requests.ts`): the UI only reads. A download button is labelled from `download_policy` of `/auth/account/status` (`approvalVerdict` holds the tracks the page knows a request would need against the server's `auto_up_to`; an admin and open mode are `applies: false` and see no change; a page that does not know the size only gets the limit as a tooltip), and says "Request" when it would wait. A 202 `pending_approval` is worded in ONE place (`useAnnouncePending`: the toast and the translated reason; also for a likes download whose job ends with `result.pending_approval`), a refusal in another (`useFailureToast`, by `error_code`), and a request that waits shows as "Waiting for approval" from the viewer's own pending list (`useWaitingRequest`: one `GET /download-requests?status=pending` shared by every button, row and tile). Users find their requests in Downloads › Requests (a tab, only for a viewer the policy governs), admins in Administration › Requests (every decision, one or many, through the batch routes, with the per-id outcome shown). The shell's `RequestsWatcher` turns the `download_request` events into the admin's pending count (the badge on Administration, its tab and the XS avatar never polls), a coalesced refresh of the admin's list and the requester's approved/denied toasts. The general policy is the generated `download_requests` group of the settings (labels and option names by key in the dictionaries, a threshold shown by `visible_when` only for `auto_up_to`); a user's override is a panel in Administration › Users (`routes/admin/UserDownloadPolicy.tsx`). The `e2e/tests/download-requests.spec.ts` spec follows a request from the user to the admin and back
- **Download resolution**: Phase 1 (every identifier each provider accepts) → Phase 2 (fuzzy, only providers with `supports_fuzzy`) → retry with exponential backoff + jitter (`core/backoff.py`, capped by `retry_max_delay_seconds`). A provider failing transiently `provider_cooldown_errors` times in a row rests `provider_cooldown_seconds` (`services/provider_cooldown.py`); a retry never comes back before the rest ends. A failure that exhausted its retries stays `retriable` and the `retry_transient_failures` routine queues it again later, a few per run
- **File state**: `core.download_states.file_state` — `downloaded` when the track is in the library (any source), else the aggregate of its attempts. Lists, phase filters, counters and live progress events (`file_state`, `phase`, via `services.progress.publish_download_progress`) all use it; the UI shows it, never an attempt's raw status. `Download.completed_at` is set iff the state is terminal
- **Compound provider ids**: a catalog whose recording lives in several releases may name a track `recording_id::release_id` — one recording in N releases produces N Track objects (intentional)
- **Auth strategy pattern**: Provider declares `AuthDefinition`, `AuthManager` executes the flow. The OAuth2 strategies are declarative data in `musizerr_sdk.auth` — a closed set of frozen dataclasses (`BasicClientAuth`/`RequestBodyClientAuth` for the token endpoint, `BearerHeaderRequestAuth`/`QueryParamRequestAuth` for calls, `ClientCredentialsFallback`/`PublicClientFallback` when no token is stored) that carry values and no code; the host implements each one in `core/auth_strategies.py`, chosen by the strategy's exact type, and refuses one it does not know (`UnsupportedAuthStrategy`). A provider can't ship auth code to the host: a new strategy is an SDK + host change. `OAuth2Config.extra_authorize_params` adds query parameters to the authorize URL (never replacing the ones `AuthManager` sets)
- **External utility intake** (`routes/external_utility.py`, `musizerr_sdk.auth.ExternalUtilityConfig`): a provider whose account is captured by a program of its own (`AuthFlow.EXTERNAL_UTILITY`) declares the name that program uses in its calls (`intake_name`), the OAuth client it borrows (`borrow_oauth_client_from`) and the fields its accounts are listed with (`account_display_fields`). The host serves `GET /credentials/{name}`, `POST|DELETE /credentials/{name}/{account}` and `GET|PUT /credentials/{name}_api_config` (admin-only, under `/api` too) for whichever provider declares the name, keeps an account as the utility sent it and hands it to the provider in `AuthSession.extra["accounts"]`; a name nobody declares is a 404. No route, constant or schema of the host names a provider or a utility
- **Provider sources** (`docs/catalog.md`, ADR-0006 phase 4; `core/catalog.py` the pure rules, `services/sources.py`, `services/gateway_sync.py`, `routes/sources.py`, `scripts/provider_sources.py`): a source is the URL of a catalog version 2 (providers as OCI images PINNED BY DIGEST with their permissions); the admin sees the permissions at install and their difference at update, and what is recorded in `installed_providers` is what was approved. The database is the only source of truth for what is installed: the host PUSHES the desired set to the gateway (`{"op": "install"}`, at start, after every change, and when the gateway restarted — `provider_events.GatewayWatcher`) and the gateway refuses an image whose labels differ from the approval. A source may carry a token (`provider_sources.credential`: stored SEALED like provider credentials — `ProviderSource.credential` opens it, `set_credential` seals it, and a token that cannot be opened is a source with none —, never returned, sent only to the catalog's host over https and to the registry of its images by the gateway, in memory). No pip, no entry points, no `installed.json`
- **Datetimes are UTC with an offset**: every datetime column is `db.types.UTCDateTime` (stored as naive UTC text, read back aware); `core.utc.as_utc` reads a naive value as UTC and `utc_iso` is the API form. The frontend parses API times with `lib/dates.parseApiDate` (a string without an offset is UTC) and its tests run in `TZ=Europe/Rome`. `tests/test_api_datetimes_utc.py` sweeps every GET route for datetimes without an offset
- **Signed preview URLs**: a provider whose preview URLs expire puts `self.context.preview_url(id)` on its tracks and implements `get_preview_url`; the host route `/preview/{provider}/{id}` resolves a fresh URL per listen and proxies it, so no cache (the discover cache, the browser's persisted copy) ever holds an expired one. The persisted query copy drops `preview_url`/`stream_url` that are not API paths. The player falls back from the full stream to the preview and, once, asks for the track again (`lib/fresh-track.refetchTrack`) before saying it cannot play
- **Session refresh**: refresh tokens rotate; re-presenting one rotated less than `services/refresh_tokens.REUSE_GRACE_SECONDS` ago answers the same successor (derived with the server secret, never stored), later it revokes the whole sign-in family. The frontend serializes the refresh across tabs (Web Locks, `authStore.withRefreshLock`) and signs out on a refused refresh only if localStorage still holds the token it sent
- **Viewer status belongs to the session** (`contexts/AuthContext.tsx`, `queryKeys.viewerStatus(scope)`): `GET /auth/account/status` answers for the bearer token, so the frontend keeps it under a scope — `anonymous` (no credentials) or `session` (an access or refresh token is held) — and the two never share an entry. A saved guest status therefore never stands in for a restored session's: with a refresh token and no access token yet the session's status is not asked (it would be answered as a guest) and only its own saved copy, if any, is read (offline); `ready` stays false (the loading screen) until a status of the current scope exists, so a route guard never decides on another viewer's. The session's status is dropped when the session ends. `routes/deep-link.test.tsx` and `e2e/tests/deep-link.spec.ts` guard it
- **Stored host URLs**: cover/stream URLs served by the backend are never persisted as URLs. `tracks.track_data` and `user_saved_track_providers.stream_url` hold prefix-free references (`hostref:/cover/provider/p/id`, `core.urls.to_host_ref`); responses rebuild them with the current `PUBLIC_API_PREFIX` through `services.stored_tracks.public_track_dict()` / `services.public_urls.publish()`. Write `track_data` only via `db.track_store.stored_track_data()`, read it only via `track_data_dict()`/`track_from_record()`. See `docs/adr/0004-stored-host-url-references.md`
- **Provider failures**: a provider failure is never a 500. A failed call reaches the host as a contract exception or a `ProviderCallFailed` (see "The host reaches a provider only through the call protocol"); `services.errors.classify_error` maps it to its `kind`, then the route to a status. Detail routes wrap the call to their provider in `services.provider_calls.provider_call(name)`; the handler in `routes/errors.py` answers 404 (provider says not found), 503 + `Retry-After` (unreachable, timeout, rate-limited, `ProviderNotConfigured`) or 502 (anything else), with `detail.error_code` and `error_detail` for admins only. Aggregated routes collect failures in a `core.provider_failures.ProviderFailures` and return `provider_errors: [{provider, error_code, error_message}]` (`services.errors.provider_errors`); an unconfigured provider is skipped, not reported. A provider whose service refuses for now (an exhausted quota that comes as a 403, a rate limit) raises `musizerr_sdk.errors.ProviderRateLimited`: classified `rate_limited`, never a refused credential nor an empty result; if the upstream says how long to wait it passes `retry_after` (seconds; for an HTTP 429 the runner reads a numeric `Retry-After` header itself) and the route's `Retry-After` is that (capped at an hour, default 30 s). A database that stays busy (SQLite lock, PostgreSQL lock timeout, deadlock, serialization failure or statement timeout) is a 503 `database_busy`
- **Streaming a stored file** (`routes/stream.py`): every step before the storage's first byte waits at most `stream_start_timeout` (`ProviderContext.stream_start_timeout`, honoured by the storage provider); a timeout or a refused connection is already "unreachable" (no second round trip to tell it from a lost file); an unreachable storage rests `storage_stream_cooldown_seconds` (`RedisProviderCooldown`, scope `storage-stream`) and meanwhile a track with a sync copy plays that copy without asking the storage
- **Library, favorites, playback** (server-decided, the UI only reads them): a track is *in the library* when a download landed, the storage holds its file (library scan) or a sync provider indexed it — `db/library_store.py`, used by the track field and every coverage. A library entry whose file the storage no longer holds is `missing_since` (set by the library file reconciliation, `services/library_reconcile.py`: routine `reconcile_library_files` and `scripts/library_reconcile.py`, dry run by default): it and the downloads that landed on its path stop counting, and outside the library a landed attempt is a `failed` file state. The reconciliation first looks for the file (current naming template, the same path ignoring case/punctuation, the sync provider's file by size) and never deletes anything `services/track_state.annotate_tracks` sets `download_status` (file state), `in_library`, `library_id`, `favorite`, `favorite_pending` and `playback {type, source}` on every track list. Favorites (`user_favorites`) are always library tracks (`services/favorites.py`); a user's download always adds a "favorite on arrival" intent (`PendingLike`), admins choose (`add_to_favorites`); likes from other providers become favorites through the like matching routine (`match_track`)
- **Worker topology** (`docs/workers.md`): three queues, one worker process each — `downloads` (download_task), `jobs` (library jobs a user starts, full-sync check), `maintenance` (tick, routines, reconciliation chains; the default queue) — and ONE beat. Routes live only in `workers/celery_app.py` (`TASK_ROUTES`, by registered name). Startup reapers run only in the worker of their queue; heartbeats are per queue. The provider registry of a worker lives in the PROCESSES THAT RUN TASKS, never in the Celery parent (`worker_init` runs there, and a prefork child would inherit a frozen copy as of fork time, usually empty because the gateway starts providers after the workers, with no reloader thread): `workers.celery_app.get_registry()` is `services/process_registry.ProcessRegistry`, which builds the registry and its own `ProviderReloader` on first use in each process (a new pid, i.e. a fork, builds again), the only place a worker builds one; the reloader also rebuilds on its first subscription when the gateway already moved past what the registry loaded. Routine runs: `queued_at` → `started_at` (real start) → `finished_at`, status `queued → running → ok|error|skipped`; due counts from the last real start, a scheduled run claims its period (`db/routine_run_store.claim_run`) so a backlog never runs a routine twice. A run executes on the queue of its routine's task (`TASK_ROUTES`, default `maintenance`); a task result `{"status": "error"}` is an `error` run (its `error_code` is kept); a routine with `follows` runs after every run of its leader and the tick holds it while the leader runs; `reports_progress` hands the task a `services.routines.RunProgress` (phase, provider, processed/total, heartbeat, shown as `last_run.progress`)
- **Library jobs** ("Sync likes", "Download the ones liked elsewhere"): `services/library_jobs.py` persists a `library_job_runs` row `queued` BEFORE enqueuing, and the trigger is idempotent per user and kind (partial unique index: one queued/running run). The worker claims it (`JobReporter.claim`, queued → running, never reviving a run closed as stale), reports generic progress (phase key, provider, processed/total, one entry per provider, heartbeat) with throttled short writes placed after its own commits, and finishes it. `reap_stale` fails runs no worker will finish: `worker_unavailable` (queued while the Redis worker heartbeat of `services/worker_health.py` is missing, or for too long), `worker_lost` (no heartbeat while running, or left running by a restarted worker). Progress is published as `library_job` events on `/progress` to the owner only; `GET /library/jobs` is the source of truth the UI polls while a job is active
- **Playlists** (`docs/playlists.md`, `services/playlists.py`, `playlist_sync.py`, `playlist_monitor.py`, `playlist_downloads.py`, `routes/playlists.py`, `db/playlist_store.py`): a playlist is the user's own, PRIVATE (`own`: edited by the owner; `followed`: a read-only mirror of a metadata provider's playlist, duplicated into an own one to edit). Every edit runs under `xact_lock("playlist:<id>")`; the cap is the system setting `playlist_max_tracks` (409 `playlist_full`, a batch is all or nothing). Following keeps the tracks and asks to download them through `download_requests.request_download` (kind `playlist`, `favorite_for=None`: they are NEVER favorites); the routine `refresh_followed_playlists` looks at each source with the owner's accounts through the provider's `get_playlist_snapshot` and applies the diff (new tracks asked for download under the policy, lost ones leave the playlist, files stay); a source that fails is `refresh_error_code` and an `error` run. The routine `sync_playlists` (FOLLOWS `sync_library_index`) pushes every user's playlists to their OWN account (`own_store`, never a shared one) on each sync provider that `supports_playlists()`, only the tracks the provider already indexed, remembered by a content hash; a deleted playlist's copy is deleted by the same run (`playlist_syncs` has no FK to the playlist). Removing a playlist keeps the tracks unless the API gets `delete_tracks=true` (a task checks again that nothing else holds them and that Musizerr downloaded them for that user). The UI reads `playlists` of the viewer capabilities
- **Related tracks**: `/track/{p}/{id}/related` = variants (`find_related_tracks`) then similar tracks (`find_similar_tracks`), each from every metadata provider in priority order, deduplicated with `match_track`. `/appears-on` uses only the variants
- **Discography download** (`POST /download/artist`, `services/discography.py`): only for a provider with `supports_discography()` (else 422 `discography_not_supported`); the artist detail carries `discography_downloadable` and `/providers/public` lists each metadata provider's `metadata_capabilities`, which is all the UI reads to show "download everything" (artist page and artist tile). The releases come from ONE provider (`get_artist_albums`, which PAGES INSIDE and honours a large `limit` — never limited by a search setting: `search_limit` is a search page size; the artist page reads `RELEASES_LISTING_LIMIT` = 100 and says `may_be_longer` when it reaches it, the download reads the whole listing up to `LISTING_LIMIT` = 200 and refuses a listing that reaches it as `discography_too_large`, since the releases of the chosen types cannot then be counted), are grouped with `group_releases` (the editions of a release are one, read through the representative) and narrowed by `release_types` (`core.discography.select_releases`; default `OWN_RELEASE_TYPES` = album, single, ep: never compilation, live or appears_on; an untyped release counts as an album). Each release is read with `get_album`, one at a time and album first, and `distinct_songs` (`core.matching.same_song`: a shared `song_keys` name and close durations, never a bare title) keeps the first copy of a song, so the album's version wins over the single's. Bounded: more than `MAX_RELEASES` releases is a 422 `discography_too_large` (never a cut list), a release that fails is counted in `releases_failed` and its failure goes in `provider_errors`, a rate-limited provider is not asked again, every release failing is the provider's own failure (502/503), nothing to take is 422 `discography_empty`. The gathered tracks go through `request_download` with `artist_spec`, so the approval policy counts `needed_tracks` from them
- **Discography grouping** (`core/discography.py`): editions of one release (`match_release`) are one entry; the same release dated differently by two providers merges only when each provider lists one release with that title/artist/type and known track counts agree. Order: `ALBUM_TYPES` order, then year desc (entry year = oldest edition), then title
- **Track format template**: `config.track_format` uses Python `str.format()` syntax. Available variables: `{artist}`, `{album}`, `{title}`, `{track_number}` (supports `{track_number:02d}` for zero-padded; when the number is unknown the placeholder and the separator after it are dropped, never "00"), `{release_year}` (falls back to `"Unknown"`). File extension is added by the download provider. Implemented in `services/library_paths.py:library_path()`
- **Versions and updates** (`docs/adr/0007-versions-compatibility-and-upgrades.md`): the git tag is the only place a version is written, and releases are automatic: every merge into master computes the next version from the labels (`breaking`, `feature`, `fix`, `chore`; checked on every pull request into dev by `.github/workflows/labels.yml`) of the pull requests merged into dev since the last tag, tags it and creates the release (`.github/workflows/images.yml`); the workflow passes the version to the builds (`MUSIZERR_VERSION`: `1.4.0`, or `1.3.2+7.abc1234` for a build of master; `dev` for the development stack), read by `services/app_version.py`, the gateway's health and the web app (`lib/version.ts`). `/health` tells it to admins only. The rules of versions and of what an upgrade implies are pure (`core/versions.py`); the routine `check_for_updates` (on by default, daily) reads the GitHub releases and their `release.json` (`services/update_check.py`) and `GET /admin/updates` judges each newer release against what runs now (the installed providers' contracts): the notice at the top of Administration (`components/updates/UpdateNotice.tsx`). Musizerr is always updated by hand
